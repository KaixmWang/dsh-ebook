# 读书使我更文艺

—— 一个把「搜书 → 取书 → OCR → 翻译 → 推送」缝成一条线的 DeepSeek Harness 插件

> 项目地址：<https://github.com/KaixmWang/dsh-ebook>

## 一、文艺的门槛，其实在工程里

「读书使我更文艺」这句话，说出来是气质，做起来是体力活。

你想读一本绝版书，通常要经历这么一串：先在几个书源之间来回搜，找到一条能用的链接；下载到一半断了，重来；下下来是个扫描版 PDF，复制不出一行字；想给 AI 读，它连目录都啃不动；好不容易看懂了，是外文；看完想同步到手机阅读器，又得导一次格式。

文艺感毁在第 2.5 步。真正拦住人的从来不是「不想读」，而是「书到不了手上」。

`dsh-ebook` 这个插件干的事很朴素：**把这条链路一次性缝好，缝到你只需要说一句「帮我把这本书弄进来」。**

## 二、一句话说清它能干什么

它是一个装在 DeepSeek Harness 里的电子书库：**搜书 → 取书 → OCR → 翻译 → 推送微信读书**。

EPUB / PDF 解析后，产出两份东西：

- 一份 **Markdown 分章正文**，给模型读；
- 一份 **人可读的 EPUB + 封面书架**，给你自己读。

也就是说，同一本书同时有了「AI 的输入格式」和「人的阅读体验」。前者决定它能不能被讨论，后者决定你愿不愿意打开它——两个都要，才叫完整。

## 三、五个工具，一条流水线

插件往会话里递了五个工具，命名起得很克制，一看就知道下一步该接什么：

| 工具 | 作用 |
| --- | --- |
| `ebook_search` | 聚合检索，按可读性排序：epub 优先、重复条目合并、超大合集降权 |
| `ebook_fetch` | 下载或读本地文件 → 解析 → 补封面与简介 → 自动 OCR → 切章 |
| `ebook_translate` | 按章翻译，逐章落盘、可断点续跑 |
| `ebook_read` | 按章读书给模型，带字数预算与 `nextStart` |
| `ebook_library` | 书架状态：章节数、字数、是否已 OCR / 已翻译、`sourcePath`、OPDS 地址 |

书源三条腿走路：**LibGen**（多镜像池）、**Z-Library**（eAPI，需账号）、**Internet Archive**。中文书名直接搜，不用先想英文关键词。

取书有两条路，都很直白：

```
书源路线：ebook_search → 拿 md5 + source → ebook_fetch
本地路线：ebook_fetch({ path: 'D:/books/x.pdf' })
```

`path` 还能接 `ebook_library` 返回的 `sourcePath`，用来对已入库的书重做 OCR——比如前 9 页糊了，只想补那几页：

```
ebook_fetch({ path: '…/source.pdf', ocr: 'force', pages: '3-9' })
```

## 四、封面墙：文艺感是长在界面上的

侧栏多了一个「书库」图标，点开是封面网格。

一本书入库时，插件会把「人判断一本书值不值得读」的那几个信号补齐：

- **封面** —— EPUB 内嵌图、PDF 首页、联网豆瓣候选，三级兜底；
- **简介与评分** —— 微信读书优先，豆瓣兜底；
- **详情页动作** —— 用系统默认程序打开、联网换封面、删除、推送到微信读书。

这不是装饰。一本只有文件名的书，在你脑子里是「资源」；一本有封面、有简介、有评分的书，才是「一本书」。**文艺是被这些细节喂出来的。**

## 五、它最容易失败的地方，恰好做得最细

电子书这件事的难点不在解析，在**下载**。单镜像取书在 LibGen 上失败率很高：镜像抽风、下载 key 过期、服务器传一半断连、慢到超时。因此取书层是分层兜底的：

| 机制 | 作用 |
| --- | --- |
| **镜像池** | 从 shadowlibraries 权威目录拉实时镜像列表（缓存在插件数据目录，24h） |
| **延迟探测** | 下载前并发探一遍，按实际延迟排序，不盲试第一个 |
| **失败冷却** | 瞬时故障（超时 / 5xx / 429）冷却 45 秒；确定性故障（403/404）本轮摘除 |
| **启动重试** | 拿不到第一个字节就退避重试，**每次重新解析直链**——镜像发的一次性 key 会过期 |
| **stall guard** | 不设全局超时。只有连续 45 秒没有新字节才判死；慢速传输不会被误杀 |
| **断点续传** | 中断保留 `.part`，重下时用 `Range` 续传 |
| **完整性校验** | 下完比对 MD5；返回 HTML 错误页会被识别并丢弃 |

这里面最值得抄的一条是 **stall guard**：大多数下载器死于一个粗暴的全局超时，把「慢」和「死」当成了一回事。这里的判据是「连续 45 秒没有新字节」——慢速传输可以一直活，真死了才死。

## 六、OCR：把扫描件重新变成字

扫描版 PDF 是 AI 阅读的头号敌人。这里的做法是有优先级的：

| 步骤 | 做法 |
| --- | --- |
| 1. 文本层优先 | PDF 自带文本层就直接用 `pdfjs-dist` 提取，绝不渲染 |
| 2. 渲染 | 无文本层的页用 `@napi-rs/canvas` 渲染成 PNG（2.2 倍缩放，上限 1700px 宽） |
| 3. 视觉识别 | 交给视觉模型逐页识别，提示词里约束了双栏顺序、页眉页脚剔除、竖排转换 |
| 4. 并发 | 多页并行（3 并发）；某页返回空文本时同页重试一次再记失败 |

提示词里那几条约束（双栏顺序、页眉页脚、竖排）是 OCR 质量的真正分水岭——模型不缺认字能力，缺的是「这一页该怎么读」的排版常识。

`ocr` 参数三档：`auto` 只补无文本层的页、`force` 全本重做、`off` 关闭。**每页一次模型调用，按页计费**，想控成本就把 OCR 模型指到一个便宜的视觉模型。

## 七、翻译：能中断，才算能用

整本翻译最怕的不是慢，是「跑到 80% 崩了，重来」。所以 `ebook_translate` 的设计是**逐章落盘、断点续跑**：重跑自动跳过已译章节，产出 `book.<lang>.md` 与 `book.<lang>.epub`。

还有一个可选项：**「翻译交给子代理执行」**。开启后每章在独立会话里翻译，可以多轮自查，代价是明显更慢；子代理失败会自动回退到直接调用。翻译质量与速度在这里是一个明确的滑杆，而不是藏在黑箱里的参数。

OCR 与翻译可以用两套不同的模型，只影响插件内部调用，不动你当前会话的模型。

## 八、最后一公里：微信读书和 OPDS

**推送微信读书**：书库详情页点一下即可，走墨水屏端接口（COS 三段导入：取凭证 → 上传 → notify）。

有个细节很懂使用者：**有多个版本时先选版本**。这本书如果已经翻译过，点推送会先列出「原书（EPUB）／中文译本（EPUB）」，点一个才推；只有一个版本就直接推，不打断操作。译本按「书名（语言）」入库，原书按书名入库。

登录支持扫码——设置页点「显示二维码」，手机微信扫一下，凭据自动保存；也支持手填 `refreshToken` 与 `deviceId`。账号卡片还显示今日配额（如 `今日 4/10`）。

**OPDS**：不占工具位。`opds.autoStart: true` 时插件加载即启动，KOReader 之类阅读器加上地址就能直接拉书。默认只监听 `127.0.0.1`，要给手机用才改 `0.0.0.0`。

Kindle 推送没有实现——但生成 `book.epub` 后自己发到 `@kindle.com` 就行，这个缺口诚实得让人舒服。

## 九、几个「为什么这么选」的技术备注

- **零外部工具依赖**：EPUB 解析与生成用自写 ZIP 读写器（`src/zip.js`，只依赖 `node:zlib`）。装个插件不该顺带装一堆二进制。
- **Z-Library 走 eAPI**：网页端有 DiamWall 保护，要执行 JavaScript 才能过；`/eapi/` 是官方客户端用的 JSON 通道，实测不经过这层保护。
- **探测接口而不是首页**：首页能开但搜索被挡很常见，探首页会给假阳性。所以「书源可达性」一键探测的是**实际接口**，LibGen 每个镜像单独列。
- **PDF 走 `pdfjs-dist` + `@napi-rs/canvas`**；OCR 与翻译走 DSH 的 `llm` 服务，复用你已配好的模型与凭据，**插件自己不留 key**。
- **网络默认读 Windows 系统代理**（Clash / V2Ray 之类），因为 Node 的 fetch 不会自动走系统代理；可用 `proxy` 配置项覆盖。
- **接口只挂本机**：`/dsh-ebook/api` 只接受本机回环或同源请求，写操作额外要求 `x-dsh-ebook: 1` 请求头（跨站请求带它会触发预检，从而被挡住）；接口不回传密码、cookie 与 refreshToken，只回「有没有存过」。

## 十、装起来

以 DSH bundle 形式分发，装进 profile 后重启 DSH 生效。在 profile 目录（`~/.dsh/profiles/<name>`）里：

```bash
pnpm add https://github.com/KaixmWang/dsh-ebook/releases/download/v0.5.2/dsh-ebook-0.5.2.tgz
```

然后把 `dsh-ebook` 加进该目录 `package.json` 的 `dsh.profile.bundles`：

```json
{ "dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "dsh-ebook"] } } }
```

也可以直接从仓库装（会拉整个仓库）：

```bash
pnpm add github:KaixmWang/dsh-ebook
```

装好侧栏出现「书库」图标，设置在该插件的详情页里（插件 → 电子书库），不占 DSH 通用设置页的位置。

## 十一、书库长什么样

```
书库/{书名}/
  source.epub | 书名.pdf      原始文件（保留原名，重名加序号）
  cover.png|jpg               封面（EPUB 内嵌图 / PDF 首页 / 联网选图）
  book.md                     给 AI 读（全书）
  book.epub                   仅 PDF 源生成；EPUB 源直接用原文件
  book.zh.md / book.zh.epub   译本
  .dsh-ebook/
    meta.json                 书名、作者、简介、评分、源文件记录
    manifest.json             章节索引
    chapters/0001-*.md        分章正文
    translated/0001.md        译文缓存
```

插件自己的数据收在 `$DSH_HOME/dsh-ebook/`：`settings.json` 与 `cache/`。**元数据、章节索引、分章正文都是插件自己的事，不该摊在书目录里**——这条边界守得干净。

## 十二、以及它做不到的

- Z-Library 需要账号，额度用完会给明确提示；
- OCR 质量取决于所配视觉模型，认不出的字用 `▢` 占位，失败页码记进 `meta.json`；
- mobi / azw3 只登记不解析，要正文请选 epub 或 pdf；
- 直连境外书源通常需要代理。

诚实列出来的限制，比一句「已完美支持」更有说服力。

## 结语

「读书使我更文艺」其实是句反话——读书不会自动让人文艺，**能顺顺利利把一本书读完**才会。

`dsh-ebook` 的全部野心就在这句话的下半截：让书到你手上的过程，短到不值得被记住。剩下的部分，才轮得到文艺。
