# dsh-ebook：搜书、读顺、哪里都能读

一条链路解决「书上不了手」：**检索 → 取书 → OCR → 翻译 → 进阅读器**。

## 六个工具

| 工具 | 做什么 |
| --- | --- |
| `ebook_search` | LibGen（多镜像自动回退）、Z-Library（需账号）、Internet Archive 聚合检索。中文书名直接搜，结果按可读性排序：epub 优先、重复条目合并、超大合集降权。 |
| `ebook_fetch` | 把书整理进书库。来源两条路：`md5 + source` 从书源下载，或 `path` 读本地文件。解析 EPUB / PDF，缺文本层的页走视觉 OCR，同时补封面与简介，切章后产出 Markdown 与分章文件。 |
| `ebook_translate` | 按章翻译，逐章落盘，中断能接着跑；已译章节默认跳过。可切换成子代理模式做多轮自查。 |
| `ebook_ask` | 就一本书提问：插件在本地读章节，交给「阅读模型」整理后只把答案带回主对话，原文不占 token。长书分批摘录再汇总。 |
| `ebook_read` | 按章读书给模型，带字数预算与 `nextStart`。原文会进主对话，只在需要逐字精读时用。 |
| `ebook_library` | 书架状态：章节数、字数、是否已 OCR / 已翻译、`sourcePath`、OPDS 地址。 |

## 书库界面

侧栏的书库图标打开封面网格，点书进详情：

- **封面**：从 EPUB 内嵌图或 PDF 首页提取；提取不到可以联网从豆瓣搜候选
- **简介与评分**：入库时自动补，微信读书优先、豆瓣兜底，缺了可以手动重取
- **推送**：推到微信读书。有译本时先列出「原书 / 译本」让你选，选哪个推哪个
- **操作**：打开文件（系统默认程序）、联网找封面、删除

## 设置面板

在**插件页 → 电子书库**里，不额外占 DSH 设置页的位置：

- **下载目录**：调系统目录对话框，选完先校验再保存
- **任务模型**：OCR / 翻译 / 阅读各配一套模型，OCR 下拉只列支持图片的；阅读模型专门给 `ebook_ask`，把读书的 token 从主模型挪走
- **本地 OCR**：OCR 模型下方的「使用本地模型（Xiaomi-OCR-0 · 0.8B）」开关，点「下载模型」自动装 GGUF 权重与 llama.cpp，之后扫描件离线识别、不花 token；装好可以切换「纯文本 / 整页 Markdown」并随时删除
- **微信读书**：扫码登录（插件内直接出二维码）、手动填凭据、删除凭据
- **取书平台账号**：Z-Library 填邮箱密码走 eAPI，卡片显示今日配额
- **书源可达性**：一键探测各镜像的实际接口，LibGen 各镜像分开列
- **关于与更新**：显示当前版本，**点按钮才**查 GitHub Releases；有新版本给提示与发布页入口，不自动安装（升级仍走 pnpm / 插件管理）

## 几个实现上的取舍

**为什么 Z-Library 走 eAPI**：站点网页端有 DiamWall 保护，需要执行 JavaScript 才能过；`/eapi/` 是官方客户端用的 JSON 通道，实测不经过这层保护。

**为什么探测接口而不是首页**：首页能开但搜索被挡很常见，探首页会给假阳性。

**为什么 EPUB 源不再生成 book.epub**：内容完全重复，一份就够；OPDS 直接把原文件发出去。

**为什么 OCR 要 attachments 服务**：视觉模型接收的是附件引用而不是裸字节，宿主没有该服务时插件会明确报错。

**为什么本地 OCR 走 llama.cpp 而不是 Python**：插件跑在 Node 里，装不动 PyTorch 那一套；社区已经把 Xiaomi-OCR-0 转成 GGUF（含 mmproj 视觉投影器），llama.cpp 的 `llama-server` 自带 OpenAI 兼容接口、能直接吃 base64 图片。于是「下载模型」= 下 500MB 权重 + 24MB CPU 运行库，插件自己起进程、自己收，全程离线。

**为什么内部数据收在 `.dsh-ebook/`**：元数据、章节索引、分章正文都是插件自己的事，不该摊在书目录里。

## 产物结构

```
书名/
  .dsh-ebook/
    meta.json        书名、作者、简介、评分、源文件记录
    manifest.json    章节索引
    chapters/        分章 Markdown
    translated/      译本（按需）
  原始文件.epub     或 书名.pdf
  cover.png|jpg     封面
  book.md            提取的全文
  book.epub          仅 PDF 源生成，内嵌封面
  book.zh.md/.epub   译本（按需），同样内嵌封面
```

**为什么生成的 EPUB 要内嵌封面**：微信读书和多数阅读器只认 EPUB 里的 `cover-image`，书目录里那张 `cover.jpg` 它们看不见；不嵌进去，推上去就是一张白板。

**为什么阅读要单独的模型**：`ebook_read` 把原文放进工具结果，这些 token 会留在主对话里并随每轮重发；`ebook_ask` 改成在插件进程内读完、用「阅读模型」整理，只回答案，原文不进对话。DSH 的工具层不支持按工具换模型，所以这条路走的是插件自己的 `llm` 调用。
